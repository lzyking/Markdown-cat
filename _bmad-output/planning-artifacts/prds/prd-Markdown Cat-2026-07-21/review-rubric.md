# PRD 质量审查报告：Markdown Cat（便携绿色 Markdown 编辑器）

**审查日期**：2026-07-21

## 1. 总体裁定（Verdict）

**adequate（可用但需修复）**

该 PRD 对 MVP 的功能范围、用户场景和非目标有清晰描述，愿景和 JTBD 与 Brief 基本一致，能够支撑下游进入 UX 与架构细化。然而，文档存在**技术实现细节侵入产品层**、**核心保存/配置路径逻辑存在可写性矛盾**、**成功指标缺乏验收方法**等关键缺陷，若不修复，将直接造成架构歧义、实现边界模糊和验收困难。建议在进入开发前至少修复以下关键项。

## 2. 分维度审查

### 2.1 Decision-readiness（决策就绪度）

**评分**：🟡 中

**发现 1（Critical）**：成功指标（§7）缺少测量方法和验收阈值，无法作为 Go/No-Go 决策依据。
- **证据**：SM-1「从双击应用到光标可用的时间 < 3 秒」、SM-2「用户连续输入 100 字，期间未发生数据丢失」、SM-3「生成的 `.md` 文件在 VS Code、Obsidian、Git 中直接打开且渲染无异常」均未说明：由谁测试、在什么硬件/系统版本上、测试几次、失败判定标准是什么。
- **影响**：团队无法判断「是否达标」，产品负责人无法据此决策上线。
- **修复建议**：为每个成功指标补充 **Measurement Method**（测量方法）、**Target**（目标值）、**Owner**（负责人）、**Pass Criteria**（通过标准）。例如：SM-1 明确为「在 macOS 14 受控测试机上，使用秒表/自动化脚本从 `.app` 双击到 CodeMirror 编辑器获得 focus，连续测量 5 次取平均值，< 3 秒通过」。

**发现 2（High）**：开放问题（§9）与假设索引（§10）将关键决策风险后置，但没有明确的关闭 Owner 与 Deadline。
- **证据**：OQ-1（企业安全策略是否限制应用目录）、OQ-2（Gatekeeper 行为）、OQ-3（是否支持拖拽打开已有文件）均标注为「需要测试/确认」，但文档中没有「由谁确认、何时确认、未确认时的默认决策」。
- **影响**：这些开放问题如果不在 Sprint 开始前关闭，将导致实现中临时返工。
- **修复建议**：为每个开放问题添加 **Decision Owner**、**Due Date**、**Fallback Decision**（如果届时无法确认，默认按哪个方案走）。

### 2.2 Substance over theater（实质而非表演）

**评分**：🟡 中

**发现 3（Critical）**：PRD 自相矛盾——声明「只陈述产品层必须做什么与为什么，不重复技术实现细节」，但正文中大量出现具体技术栈和组件名。
- **证据**：
  - §0 声明：「PRD … 不重复其中的技术实现细节，只陈述产品层必须做什么与为什么。」
  - §3 术语表：「基于 CodeMirror 6 实现」「基于 marked/markdown-it 渲染」。
  - §4.1 FR-2 Consequences：「保存操作发生在后端 Rust 层」。
  - §6.1 在范围内：「左栏源码编辑（CodeMirror 6）+ 右栏实时预览（marked）」。
  - §10 ASSUMPTION-3：「前端框架为 Vue 3，构建工具为 Vite。来源：用户确认。」
- **影响**：产品与架构职责边界模糊。技术选型应属于架构文档，PRD 中一旦写入，会让后续评审误以为这是产品需求，限制技术方案自由度；同时技术栈假设又无验收上下文（如为什么选 marked 而不是 markdown-it）。
- **修复建议**：
  1. 将所有技术实现细节（CodeMirror 6、marked/markdown-it、Rust、Vue 3、Vite）从 PRD 中移除，替换为产品层能力描述，例如「源码编辑器需支持常见 Markdown 语法输入、撤销/重做、复制粘贴」；「预览区需实时渲染源码，延迟 < 100ms」。
  2. 若某些技术约束确为产品层必须（如绿色便携、无安装），应以约束形式描述，而非组件名。
  3. ASSUMPTION-3 不应出现在 PRD 中；如确实需要记录技术栈确认，应迁移到架构文档或决策记录（ADR）。

**发现 4（Medium）**：JTBD 和成功指标的表达偏向营销语言，部分可量化的细节未落实。
- **证据**：JTBD-1「能在三秒内打开」是好的；但 JTBD-4「立即看到渲染效果」没有对应可感知的延迟阈值；SM-2「连续输入 100 字，期间未发生数据丢失」未定义「数据丢失」是否包含字符错乱、文件损坏、还是仅指未保存到磁盘。
- **影响**：测试场景设计时容易产生分歧。
- **修复建议**：将「立即」「未发生数据丢失」等表述替换为可测试的精确描述，并在 §7 中补充定义。

### 2.3 Strategic coherence（战略一致性）

**评分**：🟢 强

**认可点**：
- 愿景（§1）与目标用户（§2）紧扣「受控 Mac / 无管理员权限 / 绿色便携 / 原生 Markdown 文件」这一核心战场，没有偏离 Brief。
- 非用户定义（§2.2）和明确不做（§5）清晰排除了协作、云端、主题、Windows、多文档等诱惑，有助于团队聚焦 MVP。
- 核心假设（§1 末尾）直接对应价值主张，可验证。

**发现 5（Medium）**：「图片粘贴与附件管理」被列为「紧随 MVP 的 Should 项」，但 PRD 中没有 Should 清单或优先级，影响后续规划。
- **证据**：§5 明确不做：「图片粘贴与附件管理：MVP 不处理图片粘贴…**图片功能列为紧随 MVP 的 Should 项**，但不在本次交付范围。」
- **影响**：下游产品规划无法判断该 Should 项的优先级、依赖关系和资源安排。
- **修复建议**：在 §5 或新增「Should 候选清单」中列出紧随 MVP 的优先级项（如：图片粘贴 > 打开已有文件 > 导出 HTML），并说明排序理由。

### 2.4 Done-ness clarity（完成度清晰度）

**评分**：🟡 中

**发现 6（Critical）**：默认保存路径与配置文件路径存在「可写性」矛盾，导致完成标准模糊。
- **证据**：
  - §3 术语表：App Directory 是「应用可执行文件所在目录」，MVP 默认将 `.md` 文件保存于此；Config File 是「应用可写目录中的本地 JSON 文件」。
  - §4.1 FR-2：「新文档默认保存到 **应用目录** 下」。
  - §4.4 FR-8：「配置文件以 JSON 格式存储于**应用可写目录**（非系统目录，符合绿色应用原则）」。
  - §8 NFR-3：「运行时配置写入应用可写目录，不修改系统注册表或 `/Applications` 等系统目录」。
  - §9 OQ-1：「应用目录作为默认保存路径是否被企业安全策略限制？如果应用位于 `/Applications` 或只读挂载目录，保存会失败。」
- **影响**：
  - 当应用目录不可写时（如放在 `/Applications`、只读 DMG、企业只读挂载），FR-2 和 FR-8 会冲突：`.md` 文件存不了，配置也存不了。文档没有说明默认回退策略。
  - 「应用可写目录」和「应用目录」是否是同一个目录？术语表未定义「应用可写目录」。
- **修复建议**：
  1. 在术语表中明确定义「应用可写目录（App Writable Directory）」，并说明它是否等同于应用目录；如果不等同，给出默认路径规则（如「与应用目录同级，若不可写则回退到 `~/Library/Application Support/MarkdownCat` 或 `~/Documents/MarkdownCat`」）。
  2. 在 FR-2 和 FR-8 中统一措辞：如果默认保存路径就是应用目录，必须明确「当应用目录不可写时的回退目录和提示策略」。
  3. 在 ASSUMPTION-1 中把回退目录写死，而不是仅写「改为用户可写目录」这种模糊表述。

**发现 7（High）**：FR-5 中关于保存失败提示的持续时间自相矛盾。
- **证据**：
  - §4.3 FR-5 Consequences：「保存失败时状态栏显示失败原因，并在 5 秒内保持可见，直到用户下一次成功保存或关闭应用。」
- **影响**：实现时无法判断：是「5 秒后自动消失」还是「一直显示直到下一次成功保存/关闭应用」？两者是互斥的。
- **修复建议**：删除矛盾表述，统一为：
  - 方案 A：保存失败提示常驻，直到下一次成功保存或用户主动关闭提示；或
  - 方案 B：提示至少显示 5 秒，5 秒后自动收起，但可通过错误图标/状态继续提醒。
  选择一种方案并明确写入。

**发现 8（Medium）**：缺少明确的验收标准（Acceptance Criteria）与 Release Criteria。
- **证据**：PRD 有成功指标（§7）和 NFR（§8），但没有一页纸的「MVP 上线检查清单」或「P0 必须完成项」。
- **影响**：团队可能把功能做完就宣布完成，忽视可访问性、绿色应用验证、Gatekeeper 测试等关键上线条件。
- **修复建议**：新增「Release Criteria」章节，列出 MVP 上线必须满足的最小集合：如通过 macOS Gatekeeper 右键打开测试、在受控 Mac 上无管理员权限运行、成功指标全部达标、开放问题关闭或已记录 Fallback。

### 2.5 Scope honesty（范围诚实度）

**评分**：🟢 强

**认可点**：
- §5 非目标和 §6.2 范围外非常清晰，没有偷偷塞进功能。
- 明确不做启动恢复、手动保存、Windows 版本、多标签等，符合 MVP 精神。

**发现 9（High）**：MVP 仅支持「新建文档」，不支持「打开已有 `.md` 文件」，与 JTBD-2 的价值主张存在冲突，且 OQ-3 的开放问题没有明确决策。
- **证据**：
  - §2.1 JTBD-2：「当我写完工作日志或技术笔记后，我能以普通 `.md` 文件保存，方便后续在 Obsidian、Git、VS Code 或 Confluence 里继续使用。」
  - §9 OQ-3：「是否需要支持拖拽打开已有的 `.md` 文件？Brief 中未明确，架构也未提及，但可能是用户期望的快捷入口。」
  - §10 ASSUMPTION-7：「MVP 不处理用户手动打开已有 `.md` 文件的场景，仅支持启动时新建文档。」
- **影响**：用户后续「在 VS Code / Obsidian 里继续」使用生成的文件，但反过来想再次用 Markdown Cat 打开该文件时却无法做到，这削弱了产品作为主力轻量编辑器的价值。该假设未得到用户确认记录，属于范围裁剪风险。
- **修复建议**：
  1. 在 §5 或 §6 中明确说明「不打开已有文件」的取舍理由（如：MVP 聚焦新建记录，打开文件会引入文件管理、覆盖冲突、编码检测等复杂度）。
  2. 如果该能力对产品价值链很重要，考虑将其纳入「紧随 MVP 的 Should 项」或作为 P1 范围。
  3. 在 ASSUMPTION-7 中补充用户确认的引用或会议纪要，否则应将其改回为 OQ 并在 Sprint 前确认。

### 2.6 Downstream usability（下游可用性）

**评分**：🟡 中

**发现 10（High）**：UI 关键路径描述存在二义性，UX 设计师和开发者无法直接对齐。
- **证据**：
  - §4.4 FR-7 Consequences：「设置项位于菜单中（例如「文件 > 保存路径」或「Markdown Cat > 设置」）」。
  - §4.3 FR-5：「状态栏显示『已保存』或等效提示」。
- **影响**：菜单路径和状态栏文案都给出了多个可选方案，下游需要再开一次会确认，降低效率。
- **修复建议**：
  1. 在 PRD 中直接确定一个菜单路径（如 macOS 标准：「Markdown Cat > 设置…」或「文件 > 设置保存路径…」），把「或」删掉。
  2. 确定状态栏文案，如「已保存至 {filename}」「保存失败：{reason}」，并写入 §4.3。

**发现 11（Medium）**：术语表未定义「应用可写目录」，而它在 FR-8 和 NFR-3 中被反复使用。
- **证据**：§3 术语表定义了「应用目录」「配置文件」「保存路径」，但没有「应用可写目录」。
- **影响**：架构师和开发者对配置文件落盘位置理解可能不一致。
- **修复建议**：在术语表中新增「应用可写目录（App Writable Directory）」条目，给出 macOS 下的默认路径策略和可写性判断标准。

### 2.7 Shape fit（形态适配度）

**评分**：🟡 中

**发现 12（High）**：文件名时间戳精度不足以支持「同一秒内多次启动不覆盖已有文件」的声明。
- **证据**：
  - §4.1 FR-1：文件名格式 `New_YYYYMMDD_HHMMSS.md`。
  - §4.1 FR-2 Consequences：「文件名中的时间戳确保同一秒内多次启动也不会覆盖已有文件。」
- **影响**：`HHMMSS` 只精确到秒，如果在同一秒内启动两次，文件名完全相同，会覆盖。该声明与实现方案矛盾。
- **修复建议**：
  1. 修改文件名格式为更高精度，如 `New_YYYYMMDD_HHMMSS_mmm.md`（毫秒）或 `New_YYYYMMDD_HHMMSS_###.md`（顺序号），确保同一秒内多次启动不覆盖。
  2. 或者保留秒级格式，但修改声明为「同一秒内多次启动**可能**覆盖，建议添加顺序号/毫秒」，不要给出错误保证。

**发现 13（Medium）**：默认文件名使用 `New_` 前缀，但没有说明文件命名是否可配置或是否支持中文/特殊字符。
- **证据**：§4.1 FR-1 仅说明格式为 `New_YYYYMMDD_HHMMSS.md`。
- **影响**：如果用户保存路径包含中文或特殊字符，可能引发编码问题；如果企业有命名规范，前缀也可能不合适。
- **修复建议**：在 FR-1 或 NFR-4 中补充说明：文件名使用 ASCII 安全字符，默认前缀 `New_` 暂不可配置；路径编码统一为 UTF-8。

## 4. 可执行修复清单（优先级排序）

1. **移除技术实现细节**：将 §3 术语表、§4.1、§6.1 中的 CodeMirror 6、marked/markdown-it、Rust、Vue 3/Vite 等替换为产品能力描述；将 ASSUMPTION-3 迁移至架构/决策记录。
2. **统一保存路径与配置路径逻辑**：定义「应用可写目录」，明确当应用目录不可写时的回退目录（如 `~/Documents/MarkdownCat`），并写入 FR-2、FR-8、NFR-3 和 ASSUMPTION-1。
3. **补充成功指标验收方法**：为 SM-1 ~ SM-5 增加 Measurement Method、Target、Owner、Pass Criteria。
4. **修复文件名时间戳精度**：将格式改为 `New_YYYYMMDD_HHMMSS_mmm.md` 或添加顺序号，确保同一秒内多次启动不覆盖。
5. **明确保存失败提示策略**：统一「5 秒自动消失」或「持续到下一次成功保存/关闭」两种方案。
6. **明确 UI 关键路径**：确定菜单路径和状态栏文案，删除「例如…或…」的模糊表述。
7. **处理打开已有文件的范围决策**：确认是否纳入 MVP；若不做，补充取舍理由和用户确认引用，并纳入 Should 清单。
8. **新增 Release Criteria**：列出 MVP 上线必须满足的最小集合。
9. **关闭或 Fallback 开放问题**：为 OQ-1 ~ OQ-5 添加 Decision Owner、Due Date、Fallback Decision。

---

## 5. 结论

该 PRD 在**战略一致性**和**范围诚实度**方面表现良好，具备作为 MVP 需求文档的基本骨架。但存在三处可能直接影响交付的 Critical 缺陷：
- 技术实现细节与产品层边界不清；
- 保存路径/配置路径的可写性逻辑未闭合；
- 成功指标无法作为上线决策依据。

建议在进入架构细化和开发前，优先完成上述 9 项修复。修复完成后，该 PRD 可达到 **strong** 级别。
