## 做得好的地方

1. **优先级分层处理清晰**
   - Code review 中识别的问题按 P1/P2/Minor 分级。
   - P1/P2 问题在 review 后当场修复，不阻塞验收。
   - Minor 问题统一登记到 `deferred-work.md`，避免遗漏。

2. **代码审查闭环**
   - 每个 Story 完成后都经过 code review。
   - 修复后重新验证 `cargo check`、`npm run build`、`cargo tauri dev`。
   - 审查发现的格式问题、架构偏差都得到及时处理。

3. **错误统一结构早期落地**
   - 后端命令统一返回 `{ ok: boolean, error?: string }`。
   - 错误码使用英文常量，为后续 locale 映射打下基础。

4. **可写目录回退机制**
   - 应用目录不可写时回退到 `~/Documents/MarkdownCat`。
   - 回退目录也不可用时仍不阻断启动，符合 MVP 容错策略。

5. **团队对问题态度客观**
   - 对版本不匹配、CSP 风险、权限范围等问题没有回避，直接面对并修正。

## 遇到的挑战与教训

1. **Tauri Rust 与 NPM 包版本必须对齐**
   - Story 1.1 中遇到 `2.0.0` 与 `2.11.1` 不匹配导致构建失败。
   - 后续升级依赖后解决。
   - **教训**：Tauri 生态 Rust 端与 JS 端版本必须显式锁定，后续升级需同步检查。

2. **最小权限配置容易被忽视**
   - 初始配置中 `fs:scope` 范围过大，review 后收紧到 `$APPDATA/**/*` 与 `$DOCUMENT/MarkdownCat`。
   - **教训**：安全与权限应在第一个 Story 就明确约束，而不是后续补洞。

3. **前端降级状态需要更明确设计**
   - Story 1.4 中 `get_blank_document` 失败时，标题栏仍显示 `New_*.md` 占位名，不够真实。
   - **教训**：任何后端依赖的 UI 状态都需要设计失败降级路径，不能依赖占位字符串。

4. **Deferred work 需要定期清理机制**
   - Epic 1 积累了 8 条 deferred work 项，如果不清理会逐渐堆积。
   - **教训**：每个 Epic 开始前应扫描并清理上一轮 deferred work，避免债务膨胀。
